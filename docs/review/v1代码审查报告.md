**主要问题**

1. [include/core/thread_base.h (line 96)](/C:/Users/27013/Desktop/digital-human-sdk/include/core/thread_base.h:96) 的 `Wait(timeout_ms)` 有并发未定义行为风险。它用 `std::async` 去 `join()`，超时后主线程又对同一个 `std::thread` 调 `detach()`，两个线程同时操作同一个 `std::thread` 对象，可能崩溃或卡死；而且 `future` 析构也可能继续等待，超时语义并不可靠。建议移除强制 `detach` 路径，改成协作式停止：先确保队列/阻塞点被唤醒，再普通 `join()`；如果确实需要超时，使用平台级 timed join 或把线程生命周期改为 `std::jthread + stop_token`。

2. [src/core/audio_processor.cpp (line 126)](/C:/Users/27013/Desktop/digital-human-sdk/src/core/audio_processor.cpp:126) 队列输入模式会丢音频样本。`FillWindow()` 从 `input_queue_` 取出一个 `AudioRawPacket` 后，只拷贝 `min(space, pkt.payload.size())`，包里剩余样本没有缓存，直接丢失。大音频块或窗口空间不足时，Mel 特征时间轴会漂移。建议增加 `pending_audio_` 缓冲和 offset，直到当前包完全消费完再取下一包，并补一个“大包跨多次 FillWindow 不丢样本”的测试。

3. [src/core/pipeline.cpp (line 353)](/C:/Users/27013/Desktop/digital-human-sdk/src/core/pipeline.cpp:353) `Pipeline::Stop()` 后再次 `Start()` 会进入假运行状态。`Stop()` 在 [src/core/pipeline.cpp (line 386)](/C:/Users/27013/Desktop/digital-human-sdk/src/core/pipeline.cpp:386) 永久停止所有队列，`ThreadBase` 停止后也不能从 `STOPPED` 回到 `INIT`，但 `Start()` 不检查各 worker 的 `Start()` 返回值，最后仍设置 `running=true`。建议二选一：明确 Pipeline 是一次性对象，Stop 后拒绝 Start；或在 Start 前重新创建队列和 worker，并检查所有 `Start()` 成功后再置 running。

4. [src/core/pipeline.cpp (line 108)](/C:/Users/27013/Desktop/digital-human-sdk/src/core/pipeline.cpp:108) 没有使用 `PipelineConfig` 里的队列容量。配置里定义了 `audio_raw_queue_size`、`video_raw_queue_size` 等，但构造函数硬编码 `audio_raw_queue(0)`、`video_raw_queue(0)`，导致原始音频/视频队列无界，推理慢或输入过快时会吃光内存。建议按 config 初始化队列容量，或把无界行为显式写进配置并加入 backpressure/drop 策略。

5. [src/core/pipeline.cpp (line 483)](/C:/Users/27013/Desktop/digital-human-sdk/src/core/pipeline.cpp:483) `PipelineMetrics` 大部分指标永远是 0。`total_frames_out`、`frames_dropped`、`avg_audio_process_ms`、`avg_inference_ms` 等只在 `GetMetrics()` 读取，没有在流水线各阶段写入；实际数据在 `AudioProcessor`、`InferenceWorker`、`RenderThread` 各自维护。建议 `PipelineMetrics` 聚合各 worker 的 metrics，而不是维护一套未接线的原子计数。
